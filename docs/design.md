# 设计说明

## 一、背景

《Linux 程序设计》上机实验要求提交一份包含 18 个实验步骤的规范文档，
每个步骤包含：命令、命令含义、执行结果、终端截图、图注。

手工完成这套流程的实测耗时约 3 小时，其中**大部分时间不写字，而在反复检查有没有漏**：

- 第 7 步的图注忘了写
- 第 12 步的截图插错位置
- 第 15 步的结果描述和实际输出对不上

在几百行的文档里，这类问题肉眼极难发现。

本仓库的目标不是"自动写文档"，而是**把检查变成代码**。

## 二、流水线

```
真跑命令
   ↓  exp1.sh / exp2.sh
分段采集（带提示符）
   ↓  collect.sh
批量渲染截图
   ↓  renderer/terminal.py
按锚点自动装配
   ↓  assembler/anchors.py
断言 N 项严格一一对应
   ↓  validator/consistency.py
```

每一阶段的产物都是下一阶段的输入，中间状态可检查、可回退。

## 三、三个关键难点

### 3.1 段号漂移 —— 文本锚点定位

**问题**：Word COM 插入内容时，每插入一次，后面所有段落的编号都会变。
按固定段号定位，插入几次之后必然串位。

**解法**：不记录段号，记录一段**在文档中唯一出现的锚点文本**。
运行时全文查找它当前的位置，在它之后插入。

```
找到锚点 ──► 记录当前 index ──► 在 index + len(anchor) 处插入
```

**两条硬约束**：

1. **锚点必须唯一** —— 命中多次直接抛 `AnchorError`，绝不猜第一个。
   猜错的后果是内容插到错误位置，且很难发现。
2. **锚点必须取在内容块的最后一行** —— 否则插入的内容会把代码块从中间切断。

**批量操作必须原子**：`locate_all()` 先把所有锚点定位完，任何一个失败就整体抛错，
**不做任何插入**。半途失败会留下损坏的文档，比直接失败更难收拾。

### 3.2 多行插入顺序错乱

Word 里往同一位置连续插入多段，顺序经常是乱的。实测三种方案：

| 方案 | 实现 | 结果 |
|---|---|---|
| A | 逐行**倒序** `InsertBefore` + CR | **顺序全乱** |
| B | VT 连接后一次性 `InsertBefore` | **全挤一段，不分行** |
| C | **先建 N 段，再逐段填内容** | **正确** |

采用方案 C。原理：先一次性建好段落骨架（位置确定），再按索引逐个填文本，
插入顺序与段落顺序解耦。

### 3.3 占位符替换多出空段

`Range.Text = "xxx"` 替换占位符时，Word 会把替换文本作为一个新段落插入，
导致文档多出空段，版面被破坏。

改用 `Find.Execute`（查找替换 API），它在段落内部原地替换，不增段。

## 四、一致性校验

### 4.1 校验什么

| 维度 | 检查项 |
|---|---|
| 数量 | command / meaning / result / caption 四类条目数必须相同 |
| 配对 | 第 i 条的图注序号必须等于 i+1 |
| 唯一 | 图注文字不得重复 |
| 存在 | 每一项声明的截图文件必须真实存在于磁盘 |

### 4.2 为什么用确定性规则

**校验层不依赖任何 LLM 或 AI 判断**，全部是字符串比较、集合比较、正则匹配。

理由：如果校验本身也依赖"模型觉得这段描述对不对"，那就变成了用不确定的判断
去验证另一个不确定的结果，校验结果无法复现、无法作为 CI 断言。

现在的校验层是纯函数：同一份输入必然得到同样的输出，
可以直接写进 CI 当回归测试（见 `tests/test_pipeline.py`）。

### 4.3 图注编号的解析

图注形如「图 1-1」「图 1-2」，前半段是**实验编号**（第几个实验），
后半段才是**条目序号**（第几步）。

早期版本用 `(\d+)\s*[-–—]\s*(\d+)` 匹配并要求两个数字相等，
导致「图 1-1」被误判为"区间不合法"。

修正为只提取后半段与条目位置比对：`图\s*\d+\s*[-–—]\s*(\d+)`。

## 五、幂等与可回退

- 每次执行**从空白模板重置**，失败可无限重试，不会叠加历史内容
- 所有 Word 操作在**工作区副本**上进行，全部完成后才替换回正式文件
  （正式文件常被 WPS / editor_sdk 占用，直接操作会失败或超时）
- 采集阶段的输出带 `@@@SHOTn@@@` 标记，可精确切分回单条命令的输出

## 六、可扩展方向

- 装配层抽象出 LibreOffice UNO 实现，脱离 Windows + Word 依赖
- 增加"命令与输出是否匹配"的校验（如输出提示符是否对应该命令）
- 校验层接入 CI，作为 PR 卡点
- 采集层支持并行执行多台机器
